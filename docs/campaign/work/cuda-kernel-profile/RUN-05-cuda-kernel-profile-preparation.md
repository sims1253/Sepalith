# RUN-05 CUDA kernel profiling preparation

This packet prepares a paired `nsys` capture for the delivered Q8 inference path. It contains no GPU execution and makes no performance or quality promotion claim. The root agent must provide a fresh CUDA lease and host guard before using the command templates in [nsys-profile-plan.json](nsys-profile-plan.json).

The pinned implementation is llama.cpp b10453 at commit `3cb7ffb1a1f612d5e4a46244ae5a3c77ad934a70`. The recorded baseline is logical run `RUN-05-primary500-cuda-graph0-a`, with the Q8 model, CUDA backend, helper, and native probe identities recorded in [nsys-profile-plan.json](nsys-profile-plan.json). The scalar-only result is [RUN-05-cuda-baseline-aggregate.json](RUN-05-cuda-baseline-aggregate.json). It omits prompt text, row identifiers, token ID arrays, returned text, absolute paths, credentials, and user context.

The baseline completed eight accepted requests from four stored TRAIN mechanical fixtures: one cold request and one identical cached replay per fixture. All eight stayed within the inclusive 192 generated-ID cap, returned complete protocol records, and had no truncation. Prompt lengths were 345–1902 tokens before the manual BOS accounting shown by the native timing record. The cold aggregate had mean combined wall time 220.597 ms, median 247.764 ms, mean TTFT 136.503 ms, mean prompt evaluation 110.881 ms, and mean predicted evaluation 79.517 ms. The warm aggregate had mean combined wall time 78.585 ms, median 74.379 ms, mean TTFT 5.052 ms, mean prompt evaluation 3.758 ms, and mean predicted evaluation 69.484 ms. Warm prompt work was one token with 345–1902 cached tokens. These are unprofiled native timings; a profiler trace will have collection overhead.

The server log reports an RTX 5090, 43/43 layers offloaded, a 381-tensor Q8 model inventory (85 F32 and 296 Q8_0 tensors), flash attention enabled, a 4096 context, a 256 batch, a 1308-node graph split into two scheduler partitions, and an 8192 MiB prompt-cache limit. CUDA graph capture is already active in graph-opt=0. `GGML_CUDA_GRAPH_OPT=1` is an additional optimization that resets the stream context, requires one physical device, and interleaves eligible Q/K/V branches. The two arms therefore compare graph-opt control under the same ordinary CUDA graph capture; they do not compare “graphs off” with “graphs on”.

The source inventory in [source-inventory.json](source-inventory.json) gives exact commit-relative line anchors and hashes. The important control path is:

* `ggml_cuda_graph_compute` checks graph compatibility, waits for a stable warmup, resets on changed node properties, captures with `cudaStreamBeginCapture`, and eventually calls `cudaGraphLaunch` (`ggml-cuda.cu:4234-4290`, `3999-4215`).
* `ggml_backend_cuda_graph_optimize` enables only when `GGML_CUDA_GRAPH_OPT=1`, requires one device, detects a three-way `attn_norm` fan-out, maps branches to streams, and interleaves their nodes (`ggml-cuda.cu:4318-4560`). The code restores original branch order before fusion, so stream overlap and fusion must be measured together.
* `ggml_cuda_try_fuse` applies shape and dependency checks for RoPE/view/set-rows, binary chains, norm/RoPE, SwiGLU-style FFN, and other model-specific paths (`ggml-cuda.cu:3263-3990`). The Q8 matmul path selects MMVQ, MMQ, MMF, or cuBLAS from tensor type and shape (`ggml-cuda.cu:1812-1897`; `mmq.cu:8-176`; `mmvq.cu:480-1268`).
* Flash attention chooses tile, vector, or MMA-F16 from GQA, dimensions, masks, and tensor types (`fattn.cu:331-588`). Norm, RoPE, softmax, binary, and copy kernels are separately anchored in the source inventory.

The prepared capture wraps the existing root-owned helper, which starts the pinned CUDA server and runs the exact four-row cold/warm probe. The only arm difference is `--graph-opt 0` versus `--graph-opt 1`; each arm gets a fresh trace basename and fresh helper run name. The command uses `--cuda-graph-trace=node:host-only` so graph-node execution can be attributed, `--cuda-event-trace=true` for stream/event correlation, `--cuda-trace-all-apis=true` for graph/memory/synchronization calls, and `--trace=cuda,nvtx,osrt,cublas`. CPU sampling, context-switch tracing, CUDA memory accounting, and CUDA API backtraces are disabled to limit additional overhead. `nsys` help for every switch was checked locally without launching an application.

Root should reject a trace if it has no `llama-server` CUDA process row, if the helper hash or input identities differ, or if another CUDA workload overlaps the arm. The profiler must not be used to infer the cause of the earlier 2500-step SFT failure; that event is a driver-TDR correlation. A CUDA error or driver reset during this screen terminates the comparison.

The post-processing reports in the plan are deliberately complementary:

1. `cuda_api_sum` counts and times graph lifecycle, launch, synchronization, event, memcpy, memset, and any cuBLAS API calls.
2. `cuda_gpu_kern_gb_sum:base` gives kernel counts, total/median/min/max duration, and grid/block dimensions.
3. `cuda_kern_exec_sum:base` separates launch API, queue delay, and device execution. This is the key check for host launch overhead versus device work.
4. `cuda_gpu_mem_time_sum` identifies transfer and memset time without enabling high-overhead memory-usage tracing during capture.

The review aggregate should group kernels by stable base-name families (`mul_mat_vec_q`, MMQ, attention, norm, RoPE, softmax, copy, binary, and fused names) and report count, total, median, and tail duration for cold and warm windows. It should also report `cudaGraphLaunch`, capture, instantiate, executable-update, event, synchronization, and memcpy counts/durations; stream IDs and overlap duration; and grid/block shapes. GPU occupancy, SM activity, tensor-core activity, memory throughput, and achieved bandwidth are useful follow-up counters if the installed driver exposes them, but they are not silently substituted with a wall-time claim.

The latency decision must use paired per-fixture cold and warm native timings alongside the trace. A graph-opt candidate is worth further investigation only if it reduces the same profiled window's median TTFT or combined wall time across the paired fixtures, while preserving exact returned token identities and cap/stop status, without increasing total kernel work or queue delay. A five-percent reduction across this four-row screen is a useful investigation threshold, not an admission rule. For the Q/K/V stream optimization, report actual overlap and synchronization cost; if there is no positive overlap or if event waits dominate, leave graph-opt=1 unpromoted. For any future MPK or custom fusion binary, require a separate binary/source hash and the same paired screen. The bounded source inventory contains no existing `MPK` symbol or independent MPK switch, so it cannot be treated as an already available mode.

Sampling has two possible locations in this source. `llama_context::set_sampler` and the sampler-chain backend methods permit a backend prefix when every sampler supports backend initialization/application (`src/llama-context.cpp:1209-1264`, `src/llama-sampler.cpp:733-810`). Otherwise `common_sampler_sample` synchronizes the context and applies the CPU chain (`common/sampling.cpp:594-675`). The server's slot timing and queued-prompt accounting are separate (`tools/server/server-context.cpp:554-605`, `3938-4020`). The audit must therefore report server queue delay, CUDA kernel queue delay, device kernel time, tokenize time, and sampler time as separate quantities whenever the trace/logs expose them. TTFT is not a sampler measurement, and a full `tokens_evaluated` count is not evidence of equivalent device work under a warm cache.

The next action is root review of this packet, followed by one isolated graph-opt=0 and one graph-opt=1 trace when CUDA is released. The output is a profiling preparation artifact; no custom kernel, framework migration, server change, quality winner, or final promotion is implied.
