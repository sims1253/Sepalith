The strongest current suspect is the TorchInductor compiler pool. The independent run observation saw 24 TorchInductor compile workers under PID 3586345, and those workers were terminated with the stopped run. The installed pinned `_inductor/config.py` explicitly selects `min(32, CPU affinity)` by default and accepts `TORCHINDUCTOR_COMPILE_THREADS` before import at lines 1083–1120. The launch record contains no compiler-thread environment override, and the frozen campaign source has no compiler-thread, `torch.compile`, or Inductor configuration. The approximately 8.28 GiB commit increase at the final sample is compatible with compiler worker/process buffers and code-cache growth; per-worker RSS was not captured, so this remains a moderate-confidence attribution rather than proof.

Dynamic generation and Unsloth state are secondary suspects. In `campaign_rl_train.py:1333–1424`, one `_generate_single_turn` retains `all_prompt_ids`, `all_completions`, `all_records`, and group metadata until all calls in that update finish. `_generate_prompt_batch` creates rectangular prompt tensors and a generated sequence tensor at lines 1237–1325. The source caps this to one 32-row update, so ordinary Python record/list retention should be much smaller than the observed 8.7 GiB cliff. `campaign_sft.py:170–195` wraps generation in a `finally` cleanup that removes generation markers and calls the pinned Unsloth training restore, which reduces the case for an unbounded `_fast_lora` leak. It does not prove that all library-side caches or compiler products are released, and the CUDA caching allocator can retain reserved device memory without returning it to the host.

There is a separate avoidable setup amplification. `campaign_rl_entry.py:1027–1042` loads the selected rows for the tokenizer contract and releases them only after model load. `campaign_rl_train.py:1833–1878` then validates and loads the same rows again and creates independent dataset envelopes through `records_to_dataset_rows` (`campaign_rl_data.py:528–654, 657–661`). The first load and the second load overlap with the large model/adapter lifetime at different points, and the records and independent dataset rows overlap during trainer construction. The source also keeps the admitted recipe identity in memory for the run. This can consume substantial host headroom for the 8,440-row identity, but the source and timing do not support it as the sole cause of the final 16-second increase. Any later deduplication must preserve all row, sidecar, selected-order, source-draw, and checkpoint identity checks; it is outside this retry.

WDDM or other CUDA host accounting cannot be excluded from aggregate Windows commit. The absence of driver events, absence of CUDA OOM, stable Linux anonymous memory after termination, and the close timing of the observed compiler-worker group make WDDM a lower-confidence explanation for this attempt.
