# C12 census on vLLM: bounded Kaggle trial, 2026-10-17

**Question.** The full C12 census is 15,006 TRAIN prompts x 8 samples with a
1,024-token cap. On the bound-batching transformers path, C03 projected it at
67 to 133 Kaggle GPU-h. The user approved one bounded trial of vLLM, capped at
1 GPU-h, for the census only. Can vLLM with CUDA graphs and continuous
batching reach about 5x the bound-batching throughput (about 106 tokens/s per
two-T4 session)? Are its fp16 outputs close enough to the bf16 references to
use for the census?

**Answer.** Yes on both counts. vLLM 0.31.0 runs arm A on the T4s with fp16,
the Triton attention backend and CUDA graphs. It generated **1,143 tokens/s
per two-T4 session**, **10.8x** the 106 tokens/s baseline. At that rate the
**full census projects to about 4.0 Kaggle GPU-h** (3.8 h of generation
plus start-up), against 67 to 133 h on the bound path. Its greedy fp16 output
on DEV75 is token-identical to the bound-batching transformers fp16 run
(75 of 75). The teacher-forced target NLL matches bf16 to three decimals.
**Recommendation: run the full census (k = 8, cap 1,024) on vLLM.** Do not
shrink it. The trial used **0.33 GPU-h**.

## Engine

- **Install.** vLLM 0.31.0 with torch 2.13.0+cu130, triton 3.7.1 and
  transformers 5.17.0, in a venv. The install took 177 s and overlapped the
  model download. The vLLM and torch wheels both contain sm_75 cubins (checked
  with `cuobjdump` before the run). Kaggle driver 580 supports CUDA 13.0.
- **Engine.** One engine per T4 (two independent processes, data parallel).
  Settings: `dtype=float16`, `max_model_len` 4,096 (the C11 length policy),
  `gpu_memory_utilization` 0.88, `max_num_seqs` 256, prefix caching on.
  Prompts went in as token ids (`skip_tokenizer_init`), with stop ids 1 and
  130073. The model's `generation_config` (top_p 0.95) was ignored
  (`generation_config="vllm"`).
- **Startup.** The first configuration on the fallback ladder started on both
  GPUs. vLLM chose **TRITON_ATTN** from TRITON_ATTN and FLEX_ATTENTION;
  FlashAttention needs sm80. It compiled with torch.compile (VLLM_COMPILE,
  Inductor) and captured CUDA graphs (piecewise and full). The KV cache holds
  169,200 tokens per T4. Engine start took 150 s.

## Throughput (census sampling)

The sampling settings follow cards C12 and R4: k = 8 (`n=8`), temperature
1.0, top_p 1.0, top_k off, repetition penalty 1, cap 1,024, and one seed per
prompt (3407 + prompt index). Each worker took 256 prompts, in chunks of 32,
96, 96 and 32 prompts. The session deadline was never reached.

| | Worker 0 (T4) | Worker 1 (T4) | Session |
| --- | ---: | ---: | ---: |
| Prompts / samples | 256 / 2,048 | 256 / 2,048 | 512 / 4,096 |
| Generated tokens | 233,558 | 305,461 | 539,019 |
| Sampling seconds | 436 | 472 | 472 (slowest) |
| Tokens/s, all chunks | 535 | 648 | **1,143** |
| Tokens/s, 96-prompt chunks only | 603 | 712 | 1,266 |

The measured rate is conservative. Every chunk ends with a tail of a few long
samples running at low concurrency, and the small calibration chunks ran at
330 to 500 tokens/s. A census shard submitted as one call has a single tail.

On the same arm A, the bound-batching path is far slower than the 106
tokens/s baseline measured on the parent. Static batches wait for their
longest row, while most arm-A outputs are short. C03's fp16 runs today
reached **14.6 tokens/s** (DEV75, batch 32) and **29.8 tokens/s**
(TRAIN-200), per two-T4 session. Against that, vLLM is about 40x faster.

### Projection for the full census

Mean completion length in the trial was 131.6 tokens per sample. The
projection uses 1,143 tokens/s and adds 0.12 h of start-up per session
(model download, vLLM install, engine start).

| Census variant | Mean tokens/sample | Generated tokens | Generation h | Kaggle GPU-h |
| --- | ---: | ---: | ---: | ---: |
| **k = 8, cap 1,024 (card)** | 131.6 | 15.8 M | 3.84 | **about 4.0** |
| k = 8, cap 512 | 122.5 | 14.7 M | 3.57 | about 3.7 |
| k = 4, cap 1,024 | 131.6 | 7.9 M | 1.92 | about 2.0 |
| k = 4, cap 512 | 122.5 | 7.4 M | 1.79 | about 1.9 |

The full census fits in one 12-hour session. Two shards of about 2 h each
leave margin; the start-up overhead per shard is small. Shrinking the census
saves at most about 2 GPU-h. It would cost half the samples per prompt, which
weakens `M` (R4) and the RFT/DPO candidate yield. Capping at 512 saves almost
nothing: only 0.5% of the samples hit the 1,024 cap.

## Parity (fp16)

**References.**

- PC bf16, bound batching: the night gate's DEV75 and DEV250 evaluator cases
  for checkpoint 536.
- Kaggle transformers fp16, bound batching: C03's arm-A runs today
  (`c03-arma-dev75-fp16-b32`, `c03-arma-train200-fp16-b32`, batch 32).

vLLM's DEV greedy outputs were classified with the evaluator's own
`campaign_eval.classify`. Applied to the bf16 references, that classification
reproduces the gate counts exactly (DEV75 74/1/27/8, score250 117).

No non-finite values appeared on either fp16 path.

How to read the parity results:

- **The engine adds no measurable error.** At the same dtype, vLLM matches
  the bound-batching transformers path token for token on DEV75 and on 97.5%
  of TRAIN-200, with the same cap-hit count and mean length (121.9 vs 121.6
  tokens).
- **All the drift from bf16 comes from fp16.** The drift is the same on both
  engines: 84% identity and nofp +1 on DEV75. That is inside C03's
  count-within-1 criterion. It misses C03's 90% identity floor, and so does
  the bound fp16 path itself. On DEV250 (vLLM only), the exact edits and the
  no-op false positives are unchanged (score250 117 = 117). Five fewer
  outputs run to the cap in fp16.
- **The fp16 forward pass is accurate.** Target NLL agrees with bf16 within
  0.0006.

For census pass rates, the decisive quantities are `exact`, no-op outcome and
cap hits. Here they agree within 1 on DEV75 and exactly on edit and nofp on
DEV250. The bound-batching path stays the parity and evaluation reference;
vLLM is for census sampling only, as the user decided.

## Sampling sanity (trial subset, not the census)

These are statistics of the 4,096 samples:

- **Lengths.** Median 44 tokens, p90 380, p99 828.
- **Stops.** 99.5% stopped on EOS id 1; 22 (0.54%) hit the cap; none stopped
  on 130073.
- **Token-exact proxy** (generated ids equal the TRAIN target ids; a strict
  lower bound of reward v2.1 `exact`, which canonicalizes with air): 44% of
  samples. Prompts were 39% all-correct, 50% all-wrong and 11% mixed under
  this proxy. By family, pipe_rewrite, rename, na_rm and no_op are at or
  above 99%, format_propagation at 62%, finish_block at 6% and
  roxygen_drafting at 0%. These are not `M` or the R4 inputs. The long-output
  families are exactly where canonical comparison matters, so C12 must score
  with reward v2.1.

## Caveats and follow-ups for the census run

- **Reproducibility.** Per-request seeds make sampling reproducible only for
  the same engine, version and batch composition. Record the vLLM version,
  chunking and shard plan with the outputs.
- **Output convention.** The entry normalizes vLLM outputs to the harness
  convention (stop id kept as the last token), which reward v2.1's id check
  expects. The TRAIN-200 and DEV75 identities above confirm the convention
  matches.
- **Reward data mismatch.** Reward v2.1's `TRAIN_INPUTS` still point at the
  DAT10 **v3** rows and sidecar. Arm A was trained on, and the census samples
  from, **v4-braceindent**. Before scoring, C12 must check that the v4
  prompts and targets match what the reward references (the finish_block
  targets were re-indented in v4), or point the scorer at v4.
- **Census entry still needed.** The trial entry samples a subset. The census
  needs the full 15,006-prompt file and a shard split, submitted as one call
  per shard. It can reuse `vllm_census_entry.py`'s engine, sampling and
  record code; outputs are batched to HF in one commit (R8).
